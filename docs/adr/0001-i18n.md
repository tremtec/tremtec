# 1. Internationalization for en and pt-BR

Status: accepted. Issue: [#11](https://github.com/tremtec/tremtec/issues/11).

## Context

Copy lived in single-language modules and inline in templates, the blog and products were English only, and `<html lang>`, `og:locale` and the RSS feed were hardcoded. Astro has i18n routing but no string translation, and the app runs on Cloudflare Workers with a strict CSP and static assets served before the Worker (`runWorkerFirst: false`).

We needed `en` and `pt-BR` on every public page and in the dashboard, and adding a locale had to mean adding data, not editing templates. No i18n library and no compile step.

## URL strategy

- English has no prefix, `pt-BR` lives under `/pt-br/` (`prefixDefaultLocale: false`). Existing URLs do not change, so no redirects and no SEO loss.
- Every public page is one file under `src/pages/[...locale]/`. Prerendered pages use `localeStaticPaths()`. The server-rendered `index` and `login` answer a bodyless 404 when `parseLocaleParam` rejects the param, so `/en/...` and `/fr/...` are 404.
- App URLs (`/dashboard`, `/api`) are not prefixed. Their locale comes from the user, not from the URL.
- Path codes, cookies and the database use `en`/`pt-br`. `<html lang>`, hreflang and `Intl` use the BCP 47 tag (`pt-BR`), `og:locale` uses `pt_BR`. All of it comes from `LOCALE_INFO` in `src/domain/shared/locale.ts`.
- We have our own path helpers in `src/lib/i18n.ts` (`localizePath`, `splitLocale`) instead of `astro:i18n`. Vitest cannot import the virtual module and Hono needs the same helpers. Astro's `i18n` config is still set so it stays aligned with the sitemap.
- Each page emits absolute hreflang links plus `x-default`, and the sitemap pairs the locales. Hreflang only points at real translations.

## String storage and lookup

- Typed dictionaries, one folder per content module in `src/ui/contents/<module>/` with `en.ts`, `pt-br.ts` and `index.ts`. `en.ts` defines the shape, `pt-br.ts` is typed against it, so a missing or extra key fails `bun run lint`. `index.ts` exports `<module>Content: Dictionary<Shape>`.
- Components read `Astro.locals.locale` and index the dictionary. Interpolation is a typed function in the dictionary, plurals use `plural()` and dates and numbers use `formatDate`/`formatNumber`, all from `src/lib/format.ts` on top of `Intl`.
- Internal hrefs stay unprefixed in dictionaries and go through `localizePath` at render, so no template names a locale.
- Paraglide JS was the alternative. It adds a compiler and a runtime for what a typed `Record<Locale, T>` already gives us at build time.

## Blog and product localisation

- Posts live in `src/content/blog/<locale>/<slug>.md`. A locale lists its own posts and, for slugs it lacks, the English one, flagged as a fallback with a language badge and a link to the English URL. Post pages exist only for real translations. `src/lib/blog.ts` holds this logic as pure functions.
- Translating posts is optional and incremental: only `hello-world` is translated now, the other 13 fall back.
- Products stay in `src/content/products.json`, read through the `products` collection. Only the description varies, as a per-locale map validated by Zod, so a missing locale fails the build. Categories are stable ids, their labels live in the `products` dictionary.

## Detection and persistence

- Outside the URL the locale is always `resolveLocale`: the signed-in user's stored locale, then the `tremtec_locale` cookie, then `Accept-Language`, then `en`. It applies to app pages, API messages, login redirects and the locale stored at first sign-in.
- Inside the URL the first path segment wins. `src/middleware.ts` sets `Astro.locals.locale` on every request, and reads cookies and headers only when the request is not prerendered.
- First visit: only `/` redirects by language (`homeRedirect`). It is server-rendered, answers `302` to `/pt-br/` when the browser prefers `pt-BR` and no locale cookie exists, and carries `Vary: Accept-Language, Cookie`. Any other URL never redirects, so shared links and crawlers see what they ask for. Any locale cookie, including the one set by visiting `/login`, counts as a choice and disables the redirect.
- `users.locale` (migration `0002_add_user_locale.sql`) is a nullable `TEXT` with no `CHECK`. It is stored at first sign-in only, and an unknown stored value reads as `null`. `PATCH /api/me` changes it and sets the cookie.
- The cookie is not `HttpOnly` on purpose, so the static-page switcher can overwrite it.

## CSP-safe switchers

- The public switcher (`LocaleSwitcher.astro`) is a plain link to the same page in the other locale, so it works without JavaScript. A bundled script that imports nothing sets the cookie on click from a `data-locale-cookie` attribute.
- The app switcher (`app/shell/LocaleSelect.astro`) is a `<select>` with `hx-patch="/api/me"`, like `UserRow.astro`.
- No inline `style=` or `on*=` attributes were added, and the three drawer `onclick=` handlers in `Layout.astro` were removed.

## Consequences

- Adding a locale is data only, and the type checker lists every dictionary that is missing.
- Copy is bundled with the code, so a translation fix is a deploy. Translators work in TypeScript files.
- `/` is server-rendered, so the home page does not come from the static assets. Other public pages are still prerendered.
- Untranslated posts show up in the other locale's list in English, badged.
- pt-BR copy is a draft that a native speaker should review.
- English changes slightly: `timeAgo` says "now" instead of "just now" and the RSS `<language>` is `en`.

## Adding a locale

No template changes are needed. For a locale `xx`:

1. Add it to `LOCALES` and `LOCALE_INFO` (tag, `og:locale`, native label) in `src/domain/shared/locale.ts`. The sitemap and `astro.config.ts` `i18n` read from there.
2. Add `xx.ts` to every folder in `src/ui/contents/` (`landing`, `login`, `contact`, `services`, `not-found`, `blog`, `products`, `dashboard`, `users`), typed against the module's shape, and add its line to that module's `index.ts`. `bun run lint` lists what is missing.
3. Add the locale's description to every product in `src/content/products.json`. The build fails until all are there.
4. Optionally translate posts into `src/content/blog/xx/<slug>.md`. The others fall back to English.
5. Run `bun run lint`, `bun run test` and `bun run build`, then check `/xx/`, `/xx/blog` and the dashboard.
